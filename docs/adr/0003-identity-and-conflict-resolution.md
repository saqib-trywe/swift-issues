# Client-generated ids, server-stamped time, and link records for conflict resolution

Offline-first clients must be able to create records with no network, so every entity's primary key is a **UUIDv7 generated by whoever creates it** — client or server — rather than a server-assigned sequence; the human-facing Issue Key (`PROJ-142`) is a separate identifier the server assigns on first sync. Last-write-wins is arbitrated by the timestamp the **server** stamps at receipt, never by client wall clocks, which are skewed, user-adjustable and trivially spoofed: under client time the device with the fastest wrong clock wins every conflict forever. Set-valued data cannot be last-write-wins at all, so an Issue's Labels are not a field but a set of **link records**, each membership carrying its own id and tombstone, so two users concurrently adding different Labels both survive.

## Considered Options

- **Hybrid logical clock** (physical time plus a logical counter with bounded skew) is the rigorous answer, and unlike server-receipt time it would let a genuinely earlier offline edit beat a later one. Rejected as disproportionate for a single-team self-hosted tracker; revisit only if users report losing edits they made first.
- **Whole-set last-write-wins on labels** — rejected: it silently discards one of two concurrent label additions, which is the most likely concurrent edit there is.
- **Server-allocated integer ids** — impossible offline, and the reason the Issue Key is a second identifier rather than the primary one.

## Consequences

- "Last write wins" means last to *reach the server*, not last to be *made*. An edit made three days ago offline loses to one made five minutes ago that synced first. Accepted deliberately.
- An offline-created Issue has **no Issue Key until it first syncs**; clients render a placeholder until the server stamps one. Keys are monotonic per Project and never reused, so deleting an Issue burns its number rather than repointing old references.
- Label ids are derived deterministically as UUIDv5 over (project id, lowercased trimmed name), so two clients creating `backend` offline independently generate the *same* id and merge with no reconciliation. This is a creation-time trick only: after a rename the id no longer corresponds to the name, which is fine because the id is opaque thereafter.
- Per-field timestamps are kept for Issue's six mutable scalars (title, description, status, priority, assignee, due date), so edits to different fields don't clobber each other. Comment is versioned per record, since `body` is its only mutable field.
- **Nothing is ever hard-deleted.** Deletion sets a tombstone, retained indefinitely: to a syncing client an absent row and a never-seen row are indistinguishable, so hard deletes resurrect. Deletion is terminal and always beats a concurrent edit, because a tombstone is not a value last-write-wins can overwrite.
