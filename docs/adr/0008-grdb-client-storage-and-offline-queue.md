# GRDB for client storage, one database file, replay ordering in Swift

Client-side storage is **GRDB over SQLite**, holding the replica and the pending-operation queue in **one database file** so that applying a local mutation and enqueuing its operation is a single `write { }` transaction. Replay ordering — ADR 0004's topological, parents-before-children rule — is implemented as **a topological sort in Swift inside Core**, not as a recursive CTE in the database. The technology was deliberately chosen *last*: four other decisions determine it, and the deciding one is that the **minimum deployment target is OS 26**, applying the project's latest-*released*-only policy literally at a moment when 27 is imminent but unreleased.

## Considered Options

- **SwiftData.** Genuinely close, and **this would likely have gone the other way on OS 27**. Its non-SwiftUI change observation (`ResultsObserver`, `HistoryObserver`) is 27-only, so on 26 a background-write→UI-refresh path — exactly what a sync engine needs — is `willSave`/`didSave` plus history polling for the whole release. Beyond scheduling, two structural gaps decided it: `transaction(block:)` with `autosaveEnabled = false` makes the atomicity invariant a convention reapplied at every call site rather than a framework guarantee, and there are no partial indexes, which is precisely how quarantine-without-head-of-line-blocking is expressed. It also has no raw-SQL escape hatch at all, so a later need for FTS5 means changing storage layers rather than adding an index.
- **Hand-rolled SQLite.** Eliminated by reading the strict-concurrency gate strictly. `sqlite3 *` imports as `OpaquePointer`, which SE-0331 removed `Sendable` from, so it passes only by actor confinement the compiler cannot verify or by `@unchecked Sendable`. It also means owning several thousand lines GRDB has already debugged.
- **A recursive CTE for replay ordering.** Rejected on the principle that ADR 0004's causal ordering is a *domain contract* — it should be unit-testable without a database, reviewable by the whole team, and unchanged if storage ever changes. The real counter, recorded honestly: a CTE evaluates atomically with the read and cannot drift, while a Swift walk reads rows then computes, which is mitigated by doing it inside one transaction but is a discipline rather than a guarantee.

## Consequences

- **This decision is schedule-dependent and should be revisited if the deployment target moves to 27.** Recorded so a future reader knows it was not a verdict on SwiftData as a framework.
- **We give up `@Query`**, the fastest path to a working SwiftUI list, in exchange for roughly a day writing an `@Observable` wrapper over `ValueObservation.values(in:)`. We deliberately do **not** depend on GRDBQuery, which is pre-1.0 and unpushed since March 2025 — taking a stale pre-1.0 dependency to save work already budgeted is a bad trade.
- **We take single-maintainer bus-factor risk**, mitigated by MIT licensing, a small forkable codebase, and a thin layer over an engine with a 20-year compatibility record. This is a different risk from SwiftData's, not a smaller amount of the same one: Apple has no bus factor but is unforkable, so a blocking bug there is a radar and a wait.
- **The client store is Apple-platform-only**, which forecloses a future headless Linux sync client. Not planned. Core's models, API client and validation remain Linux-buildable because storage is a separate module those targets do not import.
- **Only the server-authoritative base record is stored**; the displayed value is that base with pending operations applied on read. The queue is already the record of what is locally dirty, so a second copy would be redundant state able to disagree with the log.
- **A tombstone arriving for an entity with pending edits drops those operations as superseded-by-deletion rather than quarantining them.** Quarantine means *repair and retry*; against a deleted entity there is nothing to retry, and leaving them pending would produce an operation that fails forever.
